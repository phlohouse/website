# Release Process Audit And Proposal

Date: 2026-05-04

Scope: Phlo release, prerelease, publish, and release-image flow, with ReleaseX source inspected in `../releasex`.

## Executive Summary

Phlo has a strong release foundation: conventional commits, release PRs, tag-driven publishing, PyPI duplicate-artifact filtering, and a recovery path for manual tag republishes. The weak spots are now mostly around prerelease repeatability, local/CI preflight confidence, and release artifact ordering.

My recommendation is to make beta releases a first-class ReleaseX channel, but not by only adding `--pre-release beta` to the current workflow. The robust version needs four changes:

1. ReleaseX must finish and ship the Python prerelease workspace work from `../releasex`.
2. Phlo should opt into explicit beta channel config and root-extra syncing once that ReleaseX build is available.
3. The GitHub workflow should use pinned ReleaseX binary versions and ReleaseX-owned publish logic, with manual publish kept only as a recovery workflow.
4. Release Docker images should install exact Phlo versions and be gated after package publication succeeds.

## Current Flow

The current release path in Phlo is:

- `.github/workflows/release.yml` runs `iamgp/ReleaseX@65c40c6...` with `release pr` on normal pushes to `main`.
- A merged `chore(release): ...` commit on `main` runs `release tag`.
- A tag push or manual `workflow_dispatch` runs the `publish` job, which builds root plus every `packages/*` workspace package and publishes all unpublished artifacts with custom Python filtering.
- `.github/workflows/publish.yml` is a separate manual PyPI workflow with similar build and duplicate-filter logic.
- `.github/workflows/build-core-services.yml` builds `phlo-observatory` and `phlo-api` images on GitHub Release publication.

Recent release history confirms the beta loop was manual-heavy:

- `v0.8.1b1` through `v0.8.1b5` were iterative beta tags.
- The napkin notes from 2026-05-03 show repeated manual fixes for beta package pins, `phlo[defaults]` prerelease resolution, runtime image prerelease behavior, and stable recovery tagging.
- Stable `v0.8.2` required a manual annotated tag after `release tag` failed with `no releasable packages found in monorepo`.

## Findings

### 1. Beta releases are not first-class in Phlo config

`relx.toml` has only the stable `main` release branch and no `[[channels]]` or `[prerelease]` sections. The ReleaseX branch in `../releasex` now contains the pieces Phlo needs:

- branch-driven beta channels
- prerelease version selection from PyPI history
- root workspace package selection for prereleases
- syncing root optional extras to selected beta workspace package versions
- `uv lock`
- root wheel metadata inspection
- PR-body install commands using `uv pip install --prerelease explicit` with exact beta pins
- finalize support for packages currently on prerelease versions

Phlo should opt into this, because it directly addresses the `b1` to `b5` pain: root extras must point at beta package versions, and verification should use exact beta pins instead of broad prerelease resolution.

### 2. ReleaseX workspace discovery is not robust enough yet

Running the current ReleaseX branch locally against Phlo exposed two discovery hazards:

- `relx status --json` failed because `packages/*` discovered `packages/.phlo`, which has no package version file.
- After trying an explicit package inventory that included `.`, ReleaseX scanned local hidden virtualenvs such as `.venv-py311` under the root package and hit third-party `__version__` values like `unknown` or empty strings before the root `pyproject.toml`.

Those are ReleaseX bugs, not Phlo package bugs. Before Phlo relies on root prerelease package selection, ReleaseX should ignore hidden directories and generated environments during Python version-file scanning, and uv workspace glob expansion should ignore hidden/non-package directories or require a `pyproject.toml`.

### 3. Publish logic is duplicated in workflows instead of centralized in ReleaseX

Both `release.yml` and `publish.yml` carry custom Python for PyPI duplicate-artifact filtering. ReleaseX now has publish idempotency and publish analysis improvements, including a fix path for tag commits that otherwise report no releasable packages.

Keeping custom publish logic in Phlo makes every ReleaseX improvement incomplete. The workflow should call `relx release publish --skip-published` once the relevant ReleaseX version is shipped, and keep the manual workflow as an emergency recovery surface.

### 4. Release tooling is not reproducibly pinned

The workflow pins the GitHub Action wrapper SHA, but the action input uses `version: "latest"`, so the downloaded `relx` binary can change between runs. That is convenient while developing ReleaseX, but not best in class for Phlo releases.

For normal releases, Phlo should pin the ReleaseX binary version explicitly, for example:

```yaml
with:
  command: release pr
  version: v1.3.0
```

After ReleaseX ships a prerelease-workspace release, update Phlo deliberately in a PR with a local dry-run transcript.

### 5. PyPI publishing still uses a long-lived token

`publish.yml` requests `id-token: write`, but both publish workflows still publish with `PYPI_API_TOKEN`. PyPI trusted publishing would reduce secret handling risk and make release provenance cleaner.

The target should be:

- configure PyPI trusted publisher for the release workflow/environment
- set ReleaseX `trusted_publishing = true` and `oidc = true`
- remove the long-lived token from the main publish path
- keep token-based publishing only as a documented break-glass recovery path if needed

### 6. Docker image releases are not tied tightly enough to package publication

`build-core-services.yml` runs on GitHub Release publication. That can happen independently from PyPI publish success. Also, `packages/phlo-api/src/phlo_api/Dockerfile` currently installs unpinned `phlo`, `fastapi`, `uvicorn`, and `pyyaml`, so a semver-tagged image can build against whatever PyPI resolves at build time.

Release images should be reproducible:

- publish packages first
- verify exact install from PyPI
- create or mark the GitHub Release as publish-complete
- build images with `PHLO_VERSION`/`PHLO_API_VERSION` args and exact pins
- smoke-test image startup before pushing semver tags

## Target Release Model

### Stable

1. Normal code PRs merge to `main`.
2. ReleaseX opens or updates one release PR.
3. CI validates the release PR with:
   - `relx validate`
   - `relx status --json`
   - `uv lock --locked`
   - wheel metadata inspection for root extras
   - `scripts/run_golden_path.py --mode dev` or a smaller release smoke if full e2e is too slow
4. Merging the release PR tags the version.
5. The tag workflow builds selected packages and publishes via ReleaseX.
6. The workflow verifies exact PyPI installs.
7. GitHub Release and release images are published after package verification.

### Beta

1. Create or update a long-lived `beta` branch from the candidate commit.
2. ReleaseX opens a beta release PR against `beta`.
3. The beta PR bumps the root package and changed workspace packages to unique `bN` versions.
4. Root extras such as `defaults` and `core-services` are rewritten to depend on selected beta workspace versions.
5. CI verifies root wheel metadata and prints exact `uv pip install --prerelease explicit` commands.
6. Beta tags publish to PyPI with prerelease classifiers and no broad `--prerelease allow` dependency resolution.
7. Workshop/blog validation installs exact beta pins from the generated command.
8. When green, `relx release pr --finalize` converts prerelease packages to stable versions.

## Proposed Phlo Config

Apply this only after ReleaseX ships the workspace-discovery fixes described above.

```toml
[[channels]]
branch = "main"
publish = true

[[channels]]
branch = "beta"
publish = true
prerelease = "b"

[prerelease]
enabled = true

[prerelease.workspace]
sync_root_extras = ["defaults", "core-services"]
```

I would not add an explicit `[monorepo].packages` inventory as the long-term fix unless ReleaseX cannot be fixed quickly. It avoids hidden directories, but it creates a second package list to maintain. The better fix is for ReleaseX to honor uv workspace semantics more carefully.

## Proposed Workflow Changes

### Release workflow

- Trigger release PRs on `main` and `beta`.
- Pass `--channel beta` only for manual beta recovery; normal beta runs should be branch-driven.
- Replace custom publish scripting with `relx release publish --skip-published`.
- Pin the ReleaseX binary version.
- Add a preflight job before publish:
  - `relx validate`
  - `relx status --json`
  - `uv lock --locked`
  - build selected wheels
  - inspect root wheel metadata for synced extras

### Manual publish workflow

Keep `.github/workflows/publish.yml`, but narrow its purpose:

- recovery only
- explicit tag input required
- dry-run default
- uses the same ReleaseX publish command
- explains when to use it in the workflow summary

### Image workflow

Change image release from "GitHub Release was published" to "package release was verified":

- either trigger from a successful release workflow with `workflow_run`
- or move image builds into the release workflow after PyPI verification
- build images with exact package versions
- run a container smoke test before pushing semver image tags

## Implementation Plan

### Phase 1: Finish ReleaseX blockers

- Ignore hidden directories and virtualenv-like directories in Python root package scans.
- For uv `members = ["packages/*"]`, include only directories with supported package manifests.
- Preserve root `pyproject.toml` as the authoritative root package version before scanning nested `__init__.py` files.
- Make errors include package root and version file path when parsing a version fails.
- Release a new pinned ReleaseX version containing the prerelease workspace work.

### Phase 2: Phlo beta channel PR

- Add `[[channels]]` and `[prerelease]` config.
- Add a beta workflow trigger.
- Run local `relx validate`, `relx status --json`, and `relx release pr --dry-run --pre-release beta`.
- Confirm the dry-run PR body includes package table and explicit install command for `defaults` and `core-services`.

### Phase 3: Publish consolidation

- Replace custom PyPI filtering scripts with ReleaseX publish.
- Convert main publish path to PyPI trusted publishing.
- Keep a documented manual recovery path.

### Phase 4: Release image hardening

- Pin package versions in Dockerfiles at release build time.
- Gate image publish on PyPI verification.
- Add image smoke checks for `phlo-api` and Observatory.

### Phase 5: Release runbook

Add a short runbook covering:

- stable release
- beta release
- beta install verification
- finalize flow
- failed tag recovery
- partial PyPI publish recovery
- image publish recovery

## Acceptance Criteria

- `relx status --json` succeeds in a normal Phlo developer checkout even when local `.venv*` directories exist.
- `relx release pr --dry-run --pre-release beta` produces a beta root version and selected beta workspace package versions.
- The beta release PR rewrites root `defaults` and `core-services` dependencies for selected beta packages.
- Built root wheel metadata contains those beta constraints.
- The PR body contains exact install commands using `uv pip install --prerelease explicit`.
- Stable publish can be rerun idempotently without custom workflow Python.
- A released `phlo-api` image installs the exact package version matching the image tag.
- The release runbook can recover from a failed publish without manually editing versions or guessing dependency pins.
